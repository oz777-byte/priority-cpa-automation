# User Journeys — 5 מסעות ליבה

כל מסע מתואר כ-flow עם נקודת כשל מזוהה. **נקודת הכשל היא מה שמעצבים סביבו.**

---

## J1 — הוספת תוכנית שותפים חדשה
**תדירות**: 1-2 בחודש · **יעד זמן**: < 5 דקות

```
עוז מזהה כלי רלוונטי
  → מחפש "affiliate program" באתר החברה
  → נרשם, מקבל אישור (שעות עד שבועיים)
  → במערכת: Offers → הוספה
  → ממלא: מודל עמלה, סכום, cookie, תנאי תשלום, URL יעד
  → המערכת מריצה evaluateOfferFit()
      ├── PASS → סטטוס active
      └── FAIL → מציגה סיבה מפורשת ("עמלה $12 < סף $25, לא recurring")
  → בדיקת end-to-end: לינק בדיקה → קליק → אימות שה-SubID הגיע לדוח
```

**נקודת כשל**: שלב בדיקת ה-end-to-end מדולג. חודשיים אחר כך מתגלה שהרשת מוחקת את ה-SubID וכל הנתונים אבודים.
**הפתרון המוצרי**: תוכנית לא עוברת ל-`active` בלי סימון `tracking_verified`. חסימה, לא אזהרה.

## J2 — פרסום נכס תוכן חדש
**תדירות**: 2-6 בחודש · **יעד זמן**: < 10 דקות (מעבר לכתיבה עצמה)

```
נבחר נושא (Phase 2: המערכת מציעה לפי פערי EPC)
  → Assets → יצירה: כותרת, נישה, מילת מפתח, סוג
  → בחירת offers רלוונטיות
  → לכל שילוב offer×placement — יצירת לינק
      → link-builder מייצר SubID + URL מקודד
  → העתקת הלינקים לתוכן
  → סימון disclosure_ok  ← בלי זה אי אפשר לפרסם (CHECK ב-DB)
  → פרסום + רישום hours_invested
```

**נקודת כשל**: `hours_invested` לא מתעדכן, ואז TimeROI חסר משמעות.
**הפתרון המוצרי**: שדה חובה במעבר ל-`published`. טיימר אופציונלי ב-Phase 2.

## J3 — ייבוא דוח עמלות ★ המסע הקריטי
**תדירות**: שבועי · **יעד זמן**: < 2 דקות

```
הורדת CSV מהרשת (Phase 2: משיכה אוטומטית ב-API)
  → Import → בחירת רשת → העלאה
  → adapter מנרמל את השורות
  → parseSubId() לכל שורה
      ├── פוענח → הצמדה ל-asset + placement
      └── לא פוענח → unattributed_conversions עם reason
  → עדכון conversions (idempotent לפי external_id)
      → כל שינוי סטטוס נרשם ב-conversion_events
  → מסך סיכום: X יובאו · Y לא הוצמדו · Z שינו סטטוס
```

**נקודת כשל**: יבוא כפול מייצר עמלות כפולות → EPC מנופח → החלטות שגויות.
**הפתרון המוצרי**: `unique(account_id, network_id, external_id)`. ייבוא חוזר מעדכן, לא מוסיף.

**נקודת כשל שנייה**: `rows_unattributed` גדל בשקט.
**הפתרון המוצרי**: מעל 10% — התראה אדומה בדשבורד. זה תסמין של tracking שבור.

---

## J4 — החלטת הקצאת זמן ★ המסע שמצדיק את המערכת
**תדירות**: שבועי · **יעד זמן**: < 60 שניות

```
פתיחת הדשבורד
  → רשימה מדורגת של פעולות:
      🔴 "עמוד X: 340 קליקים, 0 המרות → בדוק tracking או הרוג"
      🟢 "עמוד Y: EPC $2.40, מיקום 8 בגוגל → הרחב, פוטנציאל גבוה"
      🟡 "תוכנית Z: 3 המרות התהפכו → בדוק תנאים"
  → בחירת פעולה אחת → מסך הפעולה
```

**נקודת כשל**: המלצה על מדגם קטן מדי ("2 קליקים, EPC $0" → "הרוג").
**הפתרון המוצרי**: `minClicks` (ברירת מחדל 100). מתחת לזה הסטטוס הוא `insufficient_data`, לעולם לא `kill`.

## J5 — התאמת תשלומים וסגירת חודש
**תדירות**: חודשי · **יעד זמן**: < 15 דקות

```
תשלום מתקבל לחשבון
  → Payouts → רישום: רשת, סכום, מטבע, תאריך
  → המערכת מושכת שער יציג לתאריך → amount_ils
  → התאמה מול conversions בסטטוס approved
      → פער? מוצג מפורט לבירור מול הרשת
  → ייצוא דוח הכנסות חודשי לרו"ח (CSV/XLSX)
```

**נקודת כשל**: עמלה שאושרה לפני 90 יום ולא שולמה נשכחת.
**הפתרון המוצרי**: התראה על `approved` מעל 60 יום ללא תשלום תואם.

## סיכום — מה נגזר מהמסעות ל-MVP

| J1 | טופס offer + evaluateOfferFit | ייבוא אוטומטי מקטלוג רשת |

| J3 | ייבוא CSV + attribution | משיכת API אוטומטית |
| J4 | דשבורד + כללי החלטה | תחזיות, מודלים |
| J5 | רישום ידני + ייצוא | התאמה אוטומטית |
