# Playbook — חשבוניות ספק → MOVEIN.DAT → Priority

מסמך עבודה לכיסוי מלא של כל תרחישי פקודת היומן עבור חשבוניות ספק ישראליות.
זה הציר של הפרויקט — בנייה מ-POC חד-תרחישי לתשתית production רב-תרחישית.

---

## חלק 1 — צינור הנתונים (Pipeline)

```
חשבונית PDF
    ↓ (OCR + extraction)
Canonical JSON (פורמט פנימי שלנו)
    ↓ (תרחיש detector + JE builder)
MOVEIN.DAT (רשומות 180-תו לכל תנועה)
    ↓ (Priority: טעינה מתוכנות אחרות)
טבלת טעינה לתנועות יומן
    ↓ (העברה ליומן)
פקודות יומן בפריוריטי + כרטסות מתעדכנות
```

## חלק 3 — סוגי תנועה (Transaction Types)

מאומת מהזנה ידנית של טארי. **`מ` הוא תו אחד = אין בעיית RTL**, ועובד.

| קוד | שם מלא | שימוש |
|---|---|---|
| **`מ`** | תנועה מורכבת | ברירת המחדל — חשבונית ספק רגילה |
| `חס` | חשבונית ספק | משתמשי טארי משתמשים גם, אבל RTL יוצר "סח" → להימנע |
| `חרכ` | חשבונית רכש | שם חלופי — לאמת אם תקף |
| `חז` | חשבונית זיכוי / החזר | למקרי החזר מספק |
| `מז` | מזומן | תשלום מיידי במזומן |
| `הע` | העברה | תיקונים פנימיים |

**החלטה לעת עתה**: להשתמש ב-`מ` בכל המקרים. שני יכולה לסווג מחדש בעת הצורך ידנית.

## חלק 4 — 12 תרחישי JE עבור חשבוניות ספק

### תרחיש 1: חשבונית ספק רגילה (מקרה בסיסי) ✓ POC

**דוגמה**: וירטהיים 4427930 — 484.78 + מע"מ 87.22 = 572 ₪

```
DR  502-0 (קניות)            484.78
DR  205-2 (מע"מ תשומות)       87.22
CR  200087 (ספק וירטהיים)            572.00
```

**MOVEIN רשומה אחת**:
- חובה 1 = 502-0 / סכום = subtotal
- חובה 2 = 205-2 / סכום = vat
- זכות 1 = 200xxx / סכום = total

### תרחיש 2: חשבונית עם מספר הקצאה (חובה רגולטורית 2024+)

**דוגמה**: וירטהיים 4427930, הקצאה `1I4427930`, מעל רף

```
DR  502-0                    484.78
DR  205-2                     87.22
CR  200087                          572.00
פרטים: "קניות 4427930 הקצ:1I4427930"
```

**MOVEIN בפורמט 180**: שדה אסמכתא 1 = 5 ספרות אחרונות של הקצאה. מספר הקצאה מלא ב-פרטים (22 תו).

**אזהרה**: אם אסמכתא 1 צריכה להכיל ע.מ ספק (9 ספרות) ל-PCN874, **המבנה המפורט אינו תומך**. נצטרך לעבור ל-FLEXIBLE method (movein.doc + movein.prm).

### תרחיש 3: חשבונית עם שני סוגי הוצאות (קניות + שירותים)

**דוגמה**: ספק שמספק חומרי גלם (1000 ₪) + שירות התקנה (500 ₪)

```
DR  503-0 (חומרי גלם)        1000.00
DR  504-0 (שירותים)            500.00
DR  205-2 (מע"מ)               270.00  (18% × 1500)
CR  200xxx                          1770.00
```

**MOVEIN בפורמט 180** מוגבל ל-2 חשבונות חובה. **זה תרחיש שדורש 3 חשבונות חובה** (2 הוצאה + 1 מע"מ). פתרון: **2 רשומות MOVEIN** באותו עוסק:

רשומה 1 (חלק קניות):
- חובה 1 = 503-0 (1000) | חובה 2 = 205-2 (180) | זכות 1 = 200xxx (1180)

רשומה 2 (חלק שירות):
- חובה 1 = 504-0 (500) | חובה 2 = 205-2 (90) | זכות 1 = 200xxx (590)

**אסמכתא 1 = אותו ערך בשתי הרשומות** → Priority תקשר אותן.

### תרחיש 5: חשבונית עם מע"מ מנוכה חלקית (הוצאות מעורבות)

חשבונית 1180 ₪ (1000 + 180 מע"מ):

DR  502-1 (הוצאה לא מנוכה)   333.33  (1/3 × 1000)

## חלק 5 — לוגיקת מע"מ ישראלי

### שיעורים
- עד 31/12/2024: **17%**
- מ-1/1/2025: **18%**
- VAT-exempt (תיירים, ייצוא): 0%

### חישוב נכון
**אם כתוב על החשבונית** subtotal + VAT + total, להעדיף את הכתוב.
**אם יש סטיית עיגול** (subtotal + VAT ≠ total) ב-±0.05:
- שמור על total כפי שעל החשבונית
- חשב VAT = total - subtotal (טארי convention — ראינו ב-#26000473)

### סוג רשומה למע"מ (PCN874)
- `T` = תשומות (קניות) — נכלל כתשומות בדיווח 874
- `M` או `S` = מכירות
- ריק = לא מדווח (פנימי)

ב-MOVEIN בפורמט 180 — אין שדה ייעודי לזה. ב-Priority נוסף בעת ההעברה ליומן.

## חלק 6 — מספר הקצאה (חוק 2024+)

חוק חדש מ-2024: חשבוניות מעל סכום מסוים (משתנה שנתית) חייבות **מספר הקצאה** ייחודי שמופק מרשות המסים.

**רף 2024**: 25,000 ₪ (לפני מע"מ) — לעוסקים מורשים שמדווחים PCN874.
**רף 2025+**: כ-20,000 ₪ (משתנה).

חשבוניות מעל הרף ללא הקצאה = פסולות לתשומות.

**MOVEIN פורמט 180**: שדה אסמכתא 1 (5 תו) קצר. מספר הקצאה (כמו `1I4427930`) לא נכנס. **חובה לעבור ל-FLEXIBLE method עבור חשבוניות עם הקצאה**.

**לחלופין**: לאמת מול רשות המסים את הקצאה דרך API שלהם **לפני** הזנה לפריוריטי.

## חלק 7 — אילוצי MOVEIN פורמט 180

| מגבלה | משמעות | פתרון |
|---|---|---|
| אסמכתא 1 = 5 ספרות (max 99,999) | מספרי חשבונית > 5 ספרות לא נכנסים | קיצוץ ל-5 אחרונות + שמירה ב-פרטים |
| 2 חשבונות חובה max | תרחיש 3, 5, 9 לא נכנסים | מספר רשומות לאותה תנועה |
| 2 חשבונות זכות max | תרחיש 9 (ניכוי במקור) לא נכנס | אותו פתרון |
| פרטים = 22 תו | מקום מצומצם לתיאור | שימוש בקיצורים |
| אין שדה הקצאה | לא תומך ברגולציית 2024+ | FLEXIBLE method |
| אין שדה מרכז עלות | לא תומך בחלוקה לפרויקטים | FLEXIBLE method |

**החלטה ארכיטקטונית**: לבנות את ה-generator עם **שני מנועים**:
1. **MOVEIN-180** (פעיל היום) — לתרחישים 1, 6, 10, 11 (פשוטים, לא דורשים יותר מ-2 חשבונות)
2. **MOVEIN-FLEXIBLE** (לבנות הבא) — לתרחישים 2, 3, 4, 5, 9 (מורכבים, דורשים יותר שדות)

הבחירה האוטומטית: detector שבוחן את הנתונים ובוחר את ה-engine המתאים.

## חלק 8 — Validation Rules (לפני ייצוא)

לפני שמייצאים קובץ, יש לאמת:

1. **Balance check**: סכום DR = סכום CR (tolerance ±0.05)
2. **VAT rate**: 18% פוסט-2025, 17% לפני
3. **Account exists**: כל חשבון נמצא בכרטסת הראשית של טארי
4. **Supplier exists**: 200xxx קיים במאסטר ספקים
5. **Date plausibility**: תאריך החשבונית בטווח הגיוני (לא עתידי >30 יום, לא ישן >שנה)
6. **Allocation required**: סכום > רף → חובה הקצאה
7. **VAT rate × subtotal ≈ VAT amount** (tolerance ±0.05)
8. **Reference uniqueness**: לא להעלות חשבונית שכבר נטענה (לפי ע.מ ספק + מספר חשבונית)
9. **OCR confidence**: שדות עם confidence < 80% — דגל לבדיקה ידנית
10. **MOVEIN format**: 180 תווים בדיוק לכל רשומה, CP1255, CR+LF

## חלק 9 — Detector Logic (איזה תרחיש?)

```python
def detect_scenario(invoice):
    if invoice.is_credit_note:
        return Scenario.CREDIT_NOTE
    if invoice.currency != 'ILS':
        return Scenario.FOREIGN_CURRENCY
    if invoice.subtotal > ALLOCATION_THRESHOLD:
        if not invoice.allocation_number:
            return Scenario.MISSING_ALLOCATION  # ERROR — block
        return Scenario.WITH_ALLOCATION
    if invoice.has_withholding_tax:
        return Scenario.WITH_WITHHOLDING
    if len(invoice.expense_categories) > 1:
        return Scenario.MULTI_EXPENSE
    if invoice.has_mixed_deduction:
        return Scenario.MIXED_DEDUCTION
    if invoice.cost_center:
        return Scenario.WITH_COST_CENTER
    if invoice.payment_method in ('cash', 'card'):
        return Scenario.IMMEDIATE_PAYMENT
    return Scenario.STANDARD
```
